The short answer ↓

The question and the answer

BM25 finds it.
Length nearly faked it.

Before fine tuning a model like IBM Granite on math, you have to pick which training examples to use. This project treats that choice as a search problem. A math word problem is the query, and a good ranker should pull other math word problems to the top of a mixed pool.

This measures retrieval quality, not whether a model trained on the ranked data improves. That is the next step.

How the problem was solved ↓

The full solution

From a failing plan
to a clean result.

The project changed course twice. Each step below is what was done and why, in order.

  1. Step 1 · Starting pointThe original plan stalled.

    The first version ranked DeepSeek reasoning traces and fine tuned Granite on the top ranked data using Modal. Accuracy got worse after each round of ranking and retraining, and there was no GPU cluster access to scale it up.

  2. Step 2 · ReframeMeasure the ranking step on its own.

    The part that could be measured exactly was the ranker itself. So the question became an information retrieval problem: given a GSM8K math question, can a ranker put GSM8K problems at the top of a pool full of unrelated Alpaca instructions? Relevance is known for every item, so P@10, MRR, nDCG@10 and Recall@100 can be computed exactly.

  3. Step 3 · Build the testSeven rankers, three seeds, 300 queries each.

    Random, length only, TF IDF, TF IDF with Rocchio feedback, LSA, BM25, and BM25 without stop words. Each seed draws a new pool of 5,600 items and 300 new test questions. MinHash deduplication runs on a second copy of each pool, with 100 planted near duplicates to see how many it catches.

  4. Step 4 · The catchA ranker that ignores the query scored 0.47.

    Returning the longest items first, without reading the query, got P@10 0.47, about four times random. GSM8K problems are about four times longer than Alpaca items (median 42 words against 11). That shortcut inflated LSA and BM25 without length normalization, so the first leaderboard could not be trusted.

  5. Step 5 · The fixA length matched pool removes the shortcut.

    A third pool samples Alpaca items so their word counts follow the GSM8K distribution exactly. On that pool the length baseline falls below random (0.03), LSA drops from 0.89 to 0.66, and BM25 comes out on top at 0.71 with the smallest spread across seeds of any real ranker.

  6. Step 6 · VerificationChecked like a grader would.

    No GSM8K test question has an exact or near duplicate in the training set, so queries never leak into the pool. BM25 matches the reference rank_bm25 package to within 1e−12. 16 unit tests cover every ranker and metric, and a fresh clone reproduces every number on this page exactly.

The shortcut

Length was doing
the work.

GSM8K problems are long and most Alpaca instructions are short, so any method that rewards long documents gets credit for finding math without understanding anything about math. Matching lengths removes that free credit.

The lesson for any data selection project: when relevance comes from which dataset an item belongs to, check whether a trivial feature already separates the datasets.

Method

Four stages,
all on a laptop.

The whole pipeline runs on a CPU in under a minute. Select a stage for the details.

Rankers. BM25 uses k1 = 1.5 and b = 0.75 and is written from scratch on sparse matrices. Rocchio uses α = 1 and β = 0.75 over the top 10. LSA keeps 200 SVD dimensions.

Metrics. Binary relevance. nDCG uses log2 discounts with the ideal DCG from the true number of relevant items. Recall@100 has a ceiling because each pool holds more than 100 relevant items.

Data. GSM8K (MIT license) and Stanford Alpaca (CC BY NC 4.0), downloaded at run time. Near duplicates are GSM8K problems with the first number increased by 1.

Deeper checks

Tuning and scale.

A sweep over BM25's two parameters shows the same shortcut from another angle, and growing the pool shows how precision holds up as noise increases. Both use one seed.

On the standard pool the best column is b = 0, which turns off length normalization and lets long documents win. On the length matched pool that advantage disappears and b = 0.75 is best, the usual default.

Error analysis

Topic is not task.

The worst mistakes share a rare topic word with the query but are not math problems. Removing stop words makes this worse, because words like "how", "many" and "each" are the strongest sign of a word problem, and BM25 without them falls from 0.71 to 0.55 on the fair pool.

Limits

What this does not show.

Each limit points at the next experiment.

Relevance comes from the source dataset.

A real math question inside Alpaca counts as not relevant, so precision is slightly underestimated for every ranker.

Retrieval quality is not model quality.

The study does not fine tune a model on the ranked data. The next step is to train Granite on BM25 ranked and random subsets of equal size and compare GSM8K accuracy.

Only lexical and linear rankers.

A neural embedding ranker, tested on the length matched pool, is the natural next comparison.

Short near duplicates can slip past MinHash.

About a quarter of planted copies survive. One likely reason: in a short problem, changing one number removes a large share of the word 3 gram shingles, so similarity can fall below the 0.8 threshold. A unit test confirms this happens for short texts.
