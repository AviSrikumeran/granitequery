Granite Query

Before you fine tune a model like IBM Granite, you have to decide which examples are worth training on. This project treats that decision as a search problem and measures how well classic retrieval methods can find the examples that match a target task.

The problem

Training data pools are large and mixed. If the goal is to make a model better at math word problems, most of a general instruction pool like Alpaca is irrelevant to that goal. Training on everything wastes compute, and training on a random slice wastes it too.

A ranker that puts task relevant examples at the top lets you train on a small, focused subset. This project started as a full fine tuning study on Granite. Fine tuning runs on Modal got worse after each round of ranking and retraining, and there was no GPU cluster access, so the project narrowed to one question that can be answered cleanly with CS 410 tools:

Given a math word problem as a query, how well can a ranker pull math word problems to the top of a mixed training pool?

Experimental setup

Build the pool5,000 Alpaca instructions, 500 GSM8K training problems, and 100 near duplicate copies.
Label relevanceAny GSM8K item is relevant. Alpaca items are not.
Query300 GSM8K test questions. None has an exact or near duplicate in the training set.
RankSeven rankers score every pool item for every query.
ScoreP@10, MRR, nDCG@10, and Recall@100, averaged over 3 seeds.

Rankers compared

  • Random and Length only (longest items first, ignores the query) as sanity baselines.
  • TF IDF with cosine similarity, and TF IDF + Rocchio feedback, which treats the top 10 results as relevant and moves the query toward their centroid (α = 1, β = 0.75).
  • LSA: TF IDF projected to 200 dimensions with truncated SVD.
  • BM25 (k1 = 1.5, b = 0.75), with and without English stop words.

Three pools

  • Standard: the pool described above.
  • Deduplicated: the standard pool after MinHash LSH deduplication (word 3 gram shingles, Jaccard threshold 0.8).
  • Length matched: 1,800 Alpaca items sampled so their word counts follow the GSM8K distribution, plus 180 GSM8K problems and 36 near duplicates. This pool exists because of the finding in the length shortcut section.

Deduplication

The length shortcut

On the standard pool, a ranker that ignores the query and simply returns the longest items gets a P@10 near 0.47, about four times random. GSM8K problems have a median of about 42 words, while the median Alpaca item has 11. Any method that rewards long documents gets credit for finding math without understanding anything about math.

That inflates two results on the standard pool. LSA looks like the best method, and BM25 with no length normalization (b = 0) reaches a P@10 above 0.97 in the single seed sweep. Both effects mostly disappear once Alpaca items are matched to GSM8K in length. On the length matched pool, the length baseline falls below random, BM25 becomes the best ranker on P@10, nDCG@10, and Recall@100 (LSA keeps a slightly higher MRR), and b = 0.75 is the best length normalization again.

Lesson: when relevance labels come from which dataset an item belongs to, check whether a trivial feature like length separates the datasets before trusting a ranking result.

Pool size

Keeping 500 GSM8K problems and 100 near duplicates fixed while adding more Alpaca noise (one seed, 300 queries per size). As relevant items become a smaller share of the pool, precision drops for every ranker, but BM25 stays well above random.

Error analysis

The highest scoring mistakes share a pattern. The query and the retrieved item share a rare topic word, like jeans, Celsius, or bus, but the retrieved item is not a math problem. Word overlap captures topic and misses task type. Removing stop words makes this worse, because words such as "how", "many", and "each" are the strongest signal that a text is a word problem.

Live demo

Search a 3,360 item pool (3,000 Alpaca, 300 GSM8K, 60 near duplicates) with BM25 running in your browser. Type a math word problem or pick an example. Green badges mark GSM8K items.

Limitations and next steps

  • Relevance is defined by source dataset. A real math question inside Alpaca counts as not relevant, so precision is slightly underestimated.
  • The evaluation measures retrieval quality, not whether a model trained on the ranked subset gets better. Connecting the two by fine tuning Granite on ranked versus random subsets is the original goal and the next step.
  • All methods are lexical or linear. A neural embedding ranker is a natural comparison once length is controlled.

Run it yourself

Everything runs on a laptop CPU in about a minute. No GPU or API key is needed.

git clone https://github.com/avisrikumeran/granite-query
cd granite-query/ranking_study
pip install -r requirements.txt
python download_data.py
python run_experiments.py
python build_site.py
python -m unittest discover -s tests

Results are written to ranking_study/results/results.json, and this page is rebuilt into docs/index.html.
